# ROADMAP — フェーズ別の実装計画と検収条件

最終更新：2026-10-26（Phase 1）

各Phaseの終わりに **①実物の画面（PNG）②検収条件の結果 ③次Phaseの判断事項** を報告し、承認を受けてから次に進む。
目安の「ラリー」は、報告→フィードバック→修正の往復の想定回数。

---

## 変更提案：Phase 2 を前半・後半に分ける

元の計画は「Phase 2＝案件管理・シナリオデータ・フロー編集」「Phase 3＝6施策の統合」。
これだと、**6施策が要求するデータ構造を確かめる前にフロー編集画面を作る**ことになり、Phase 3 で編集画面の作り直しが起きやすい（REQUIREMENTS C-10）。

そこで Phase 2 を2段に分ける。Phase の数・順番・最終成果物は変わらない。

| | 中身 | 画面 |
|---|---|---|
| **Phase 2a** | エンジン・スキーマ・検証・CLI通し実行。検証案件のJSONを手で書き、4人で Day 30 まで流す | なし（CLIの出力のみ） |
| **Phase 2b** | 案件管理・フロー編集画面 | あり |

影響：Phase 2 の最初の報告では画面が出ない（CLIの実行結果の表で報告する）。その代わり、Phase 3 以降の手戻りが小さくなる。

## Phase 2b：案件管理・フロー編集

### 作るもの

- 開発サーバーの保存API（読み込み・保存・複製・削除＝ゴミ箱・履歴）
- 案件一覧画面（新規・複製・削除・JSONインポート／エクスポート）
- フロー編集画面（React Flow）：ノードの追加・削除・移動・接続・接続変更
- ノード設定パネル：ノード種別ごとの入力欄
- 部品の編集画面：文面・タグ・CV・経路・アンケート・リッチメニュー・自動応答・Webページ・ペルソナ
- 条件式の入力：この段階では**テキスト入力（JSON）＋その場の検証**。ビルダー型GUIは Phase 4
- 検証結果の一覧（クリックで該当ノードへ）

### 検収条件

- [ ] `start.bat` のダブルクリックで編集ツールが開く（初回は依存の自動導入）
- [ ] 検証案件を画面で開くと、フローがチャートで表示される
- [ ] ノードを追加・接続・削除して保存 → 再読み込みで同じ状態に戻る
- [ ] 保存のたびに履歴が増え、過去の版に戻せる
- [ ] 複製した案件を編集しても、元の案件は変わらない
- [ ] JSONエクスポート → 別名でインポート → 同じ内容
- [ ] 存在しないノードに繋ぐと、検証一覧に重大エラーが出て、クリックでそのノードへ飛ぶ
- [ ] 保存途中でブラウザを閉じても `project.json` が壊れない

## Phase 3：LINE／Web画面と6施策の統合

### 作るもの

- `packages/player`：素のDOMで描く画面部品
  - スマホ枠・トーク画面・吹き出し（テキスト／画像／ボタン／カード）
  - リッチメニュー（画像あり／ラベルのみ）
  - Webページ（LP・フォーム・サンクス）とポップアップ
  - アンケート回答の画面
- 6施策の操作：メニュータップ／キーワード送信／アンケート回答／ステップの到着／離脱操作→ポップアップ／フォーム送信→サンクス→友だち追加
- 編集ツールに「デモ」タブ（1ユーザー・手動進行のみ）

### 検収条件

- [ ] 経路A（離脱→ポップアップ→友だち追加→挨拶→アンケート→タグ→分岐→ステップ）を、画面の操作だけで最後まで通せる
- [ ] 経路B（応募フォーム→応募完了→サンクス→友だち追加→挨拶→…）も同様
- [ ] リッチメニューのセルを押すと、トークに発言が出て自動応答が返る／Webページに切り替わる
- [ ] 同じキーワードでも、タグによって返答が変わる
- [ ] Phase 2a の CLI の結果と、画面で同じ操作をしたときの配信履歴が一致する
- [ ] PNGで見て、提案資料に貼れる視認性がある（文字の潰れ・はみ出しがない）

## Phase 4：複数ユーザー・時間操作・裏側の可視化

### 作るもの

- ユーザー一覧（ペルソナから作成・切替・リセット）
- 時間操作：Day の進む／戻る・任意時刻へのジャンプ・イベント投入
- 自動再生：再生／一時停止／再開／速度（×1・×2・×5）。回答が要る場面で止まる。ペルソナの台本で自動回答
- 裏側パネル：タグ・属性・配信履歴・進行中フロー・判定の木（届いた理由／外れた理由）
- 「このメッセージは誰に届く？」の横断表
- 表示切替：裏側あり／画面のみ／資料用 16:9
- 説明カード（案件JSONの narration）
- 条件式のビルダー型GUI（AND／OR／NOT をブロックで組む）
- （G-6 採用時）通数カウンタ

### 検収条件

- [ ] 4人を作り、Day 7 でユーザーを切り替えると、画面・タグ・配信履歴がその人のものに変わる
- [ ] 大阪希望さんを選んで東京向け配信を見ると、「東京希望のタグが無い」ことが判定の木で赤く示される
- [ ] Day 7 → Day 3 に戻ると、Day 3 時点の状態に正しく戻る
- [ ] 自動再生がアンケートで止まり、回答すると再開する。台本ありのペルソナは止まらずに流れる
- [ ] 速度を変えても結果は変わらない（表示の速さだけが変わる）
- [ ] 資料用表示で切り取ったPNGが、16:9スライドに余白なく収まる
- [ ] 4人・Day 30 の早送りが1秒以内

## Phase 5：HTML出力・検証機能

### 作るもの

- `tools/export.ts` と編集画面の「書き出し」ボタン
- 書き出し前検証（重大エラーで中止・警告は一覧表示して続行可）
- 社内項目の除去と、書き出し後の混入検査
- 画像の縮小・埋め込みと、サイズ判定
- 営業用HTMLの見た目（編集タブなし・「架空のデータによるデモです」のフッター）
- 検証ルールの残り（警告の全種）

### 検収条件

- [ ] 検証案件を書き出し、**Wi-Fiを切った状態で** Chrome と Edge それぞれで開いて、Phase 3・4 の操作が全部できる
- [ ] 書き出したHTMLを検索して、`_internal`・社内メモの文言・編集ツールのコード・`http` で始まる外部参照が0件
- [ ] 重大エラーを1つ仕込むと書き出せない。警告だけなら書き出せる
- [ ] ファイルサイズが 3MB 以下（検証案件）
- [ ] 編集ツールのデモタブと、書き出したHTMLで、同じ操作をしたときの結果が一致する
- [ ] Downloads 直下に `<案件名>_デモ_YYYYMMDD.html` で出る

## Phase 6：スクショ解析とシナリオ生成のワークフロー・最終検証

### 作るもの

- 手順書：既存OAのスクショを Claude Code に渡し、シナリオ差分JSONを作らせる手順
  - 何を撮るか（リッチメニュー・挨拶・自動応答・配信例）
  - Claude Code への依頼文の雛形
  - 出所の付け方の決まり（画面に写っている＝observed／それ以外＝inferred）
- 差分のプレビュー・項目別の承認／却下画面
- 出所バッジ（確認済み／AI推定／承認済み）の表示
- 別業種のサンプル案件1つ（例：美容・不動産のどちらか）を差分から作って、エンジンを変えずに動くことを確認
- 最終の通し検証

### 検収条件

- [ ] 架空OAのスクショ3〜5枚から、Claude Code が差分JSONを出し、編集ツールで読み込める
- [ ] 差分の中で、スクショに写っていない分岐・タグはすべて「AI推定」になっている
- [ ] 未承認の推定が残っていると書き出せない。全部承認すると書き出せる
- [ ] 2つ目の業種の案件を、**エンジンのコードを1行も変えずに**作って動かせる
- [ ] GOAL.md §3 の完成条件のチェックがすべて埋まる
