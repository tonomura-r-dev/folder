# REQUIREMENTS — 機能要件・非機能要件

最終更新：2026-10-26（Phase 1）

番号は `FR-xx`（機能）／`NFR-xx`（非機能）。ROADMAP の検収条件はこの番号で参照する。
**【追加提案】** と付いた項目は元の指示に無く、Phase 1 で不足と判断して提案するもの。採否は承認待ち。

## 0. 既存デモ（八十吉_通しデモ.html）の分析

### 0.1 構成

| 項目 | 中身 |
|---|---|
| 形式 | 単一HTML（約36KB）。JSライブラリなし・ビルドなし |
| 外部依存 | **Google Fonts の stylesheet 1本のみ**（＝オフラインでは代替フォントになる） |
| 画面 | 3列グリッド：スマホ枠（320px）／裏側パネル4枚／説明カード。1000px・700pxで段組みが崩れる |
| スマホ時 | 説明→画面→「いま見るべき裏側1枚」の順。前へ／次へは画面下に固定。左右スワイプ対応 |
| テーマ | CSS変数でライト／ダーク両対応（`prefers-color-scheme` ＋ `data-theme` の上書き） |
| 操作 | 場面チップ／前へ・次へ／矢印キー／スワイプ／砂場フォーム（自分で予約を入れる） |

### 0.2 動作の仕組み

```js
scenes = [ { label, node, panel, before(), screen(), html, who[] }, ... ]
go(idx) { for (k = 0; k <= idx; k++) scenes[k].before(); render(); }
```

- **場面の配列が台本**。各場面が「上のパイプラインのどこを光らせるか（node）」「どの裏側パネルを強調するか（panel）」「状態をどう変えるか（before）」「スマホに何を描くか（screen）」「説明文（html）」を持つ。
- **任意の場面へ飛ぶと、0番から順に `before()` を全部やり直して状態を再構築する。** 0番の `before()` が初期化を兼ねている。
- 空席数は `slots()` が本物のアルゴリズム（滞在120分の重なりのピーク）で計算している。
- 描画は毎回 `innerHTML` で全部描き直し。差分更新なし。

### 0.3 流用する考え方

| 八十吉デモの要素 | 新ツールでの姿 |
|---|---|
| 場面配列＝宣言的な台本 | シナリオデータ（フロー＋ノード）をJSONで持つ |
| ユーザー画面と裏側パネルの同時表示 | デモモードの基本レイアウト（FR-50） |
| 0番からやり直して状態を作る | **イベントソーシング**：入力イベント列から状態を毎回導出する（DATA_MODEL §6）。「任意のDayへ戻る」「再現性」がこれでタダで手に入る |
| 「いま動いている人」パネル | 判定理由パネル（誰が・なぜ対象／なぜ除外） |
| 砂場フォーム | 手動イベント投入（FR-61） |
| パイプラインの on／done 表示 | フロー進行表示 |
| 説明文中の「★＝確認待ち」 | 出所バッジ（確認済み／AI推定／承認済み）（FR-80） |
| ビルドなし単一HTML・CSS変数テーマ | 営業用HTMLの書き出し形式 |
| `prefers-reduced-motion`・`:focus-visible`・表の上ではスワイプしない配慮 | そのまま踏襲 |

### 0.4 流用しないもの

| 要素 | 理由 |
|---|---|
| グローバル変数を `before()` が直接書き換える | 場面が増えると壊れる。状態は純関数で導出する |
| 業務ロジック（`slots()`・総席数・営業時間）がデモ本体に入っている | 共通エンジンに業種固有のルールを入れない（要件§12） |
| 説明文が生のHTML文字列 | GUIで編集できない・検証できない。構造化データにする |
| `.replace('<dd>—</dd>', …)` での数値差し込み | 正式なバインド（`{{var}}` 置換）にする |
| Google Fonts の読み込み | オフライン要件に反する。システムフォント（メイリオ）にする |

## 1. 機能要件

### 1.1 案件管理（ローカル編集ツール）

| ID | 要件 |
|---|---|
| FR-01 | 案件の新規作成（空の雛形 or 既存案件から） |
| FR-02 | 案件の複製（ID・作成日は振り直し、中身は全コピー） |
| FR-03 | 保存・読み込み・削除（削除は「ゴミ箱」へ移動。完全削除はしない） |
| FR-04 | 変更履歴：保存のたびに全文スナップショット。一覧から任意の版に戻せる |
| FR-05 | JSONインポート／エクスポート（スキーマ検証つき。古い版は自動マイグレーション） |
| FR-06 | 案件設定：会社名・アカウント名・アイコン・配色・画像 |
| FR-07 | **シナリオ設定（案件JSON）とデモ中のユーザー状態（セッション）を別ファイルで持つ** |

### 1.2 シナリオ編集

| ID | 要件 |
|---|---|
| FR-10 | フローチャート形式の編集画面 |
| FR-11 | ノードの追加・削除・移動・接続変更 |
| FR-12 | 基本ノード10種：メッセージ／画像／リッチメニュー切替／ボタン選択／アンケート／タグ付与／条件分岐／待機（ステップ）／外部ページ遷移／終了 |
| FR-13 | **【追加提案】** 入口ノード（友だち追加・キーワード・メニュータップ・CV・離脱・手動）と、別フロー呼び出しノード。入口が無いとフローの起点を表せない |
| FR-14 | 条件式：AND／OR／NOT の入れ子。葉はタグ・アンケート回答・行動履歴・経過時間・CV状態・配信済み判定・流入経路・属性 |
| FR-15 | 配信制御：フローごとに優先順位。既定は「優先度の高いフローが動いている間、低いフローは保留」。フロー単位で「並行配信を許可」を指定可 |
| FR-16 | 重複配信の防止：同一ユーザーに同一メッセージを指定期間内に2回送らない（期間は案件設定） |
| FR-17 | 停止条件：フローごとに条件式で指定（例：応募CV済み）。満たした時点で待機中のタイマーを破棄 |
| FR-18 | メッセージ・リッチメニュー・アンケート・自動応答・Webページ・ポップアップを、フローから参照する部品として個別に編集できる |

### 1.3 LINE施策（6領域）

全施策は**同じユーザー状態・同じシナリオデータ**の上で動く。独立した画面の寄せ集めにしない。

| ID | 施策 | 必須の動き |
|---|---|---|
| FR-20 | リッチメニュー | メニュー表示／セルのタップ／ページ遷移／トークへのメッセージ送信／**ユーザーごとのメニュー切替**（タグで出し分け） |
| FR-21 | 自動応答 | キーワード判定（完全一致・部分一致）／返信／条件別の応答（同じ語でもタグで返答を変える） |
| FR-22 | アンケート | 質問・選択肢（単一／複数）／回答の保存／回答ごとのタグ付与／回答による分岐 |
| FR-23 | ステップ配信 | 友だち追加からの経過（分・日）＋配信時刻／タグ・回答による分岐／配信条件／停止条件／配信履歴 |
| FR-24 | 離脱防止ポップアップ | Webページ表示→離脱操作→ポップアップ→友だち追加→挨拶→後続ステップ |
| FR-25 | サンクスLINE誘導 | フォーム入力→CV完了（応募・予約等）→サンクスでLINE誘導→友だち追加→挨拶→後続シナリオ |
| FR-26 | **【追加提案】** ブロック | ユーザーが「ブロック」すると以降の配信が止まり、除外理由に「ブロック中」と出る。LINE提案ではブロック率の説明が必ず出るため |

### 1.4 複数ユーザー

| ID | 要件 |
|---|---|
| FR-30 | 架空ユーザーを複数作成（初期値テンプレート＝ペルソナから作る） |
| FR-31 | ユーザーごとに個別管理：名前・属性・流入経路・タグ・アンケート回答・行動履歴・配信履歴・CV状態・シナリオ進行状況 |
| FR-32 | ユーザー切替で、LINE画面・内部状態・判定結果がすべて切り替わる |
| FR-33 | 配信の**対象理由**と**除外理由**の両方を、条件式のどの葉で決まったかまで表示 |
| FR-34 | 「このメッセージは誰に届く／届かない」をユーザー横断の一覧で見られる |

### 1.5 デモモード

| ID | 要件 |
|---|---|
| FR-50 | ユーザー画面（LINE or Web）＋裏側の連動表示 |
| FR-51 | 裏側の表示項目：タグ／属性／条件判定結果／配信履歴／実行中のシナリオ／各処理の説明 |
| FR-52 | 表示切替：「ユーザー画面＋裏側」／「ユーザー画面のみ」 |

| FR-54 | 各処理の説明文は案件JSONに持たせ、編集ツールで書ける（八十吉デモの説明カード相当） |

### 1.6 時間進行

| ID | 要件 |
|---|---|
| FR-60 | 手動：任意のDayへ進む／戻る |
| FR-61 | 手動：特定のイベントを発生させる（メニュータップ・キーワード送信・回答・離脱・フォーム送信・CV・ブロック） |
| FR-62 | 手動：任意時点の状態を確認する |
| FR-63 | 自動再生：再生・一時停止・再開・速度変更 |
| FR-64 | 自動再生：回答が必要な場面で一時停止。**【追加提案】**「台本どおり自動で答える」設定をペルソナに持たせ、無人で最後まで流せるようにする |
| FR-65 | 仮想時間は全ユーザー共通。同じ時刻でユーザーごとの状態に応じて別の処理が走る |
| FR-66 | 同じ入力からは必ず同じ結果になる（決定論）。提案資料に貼ったスクショを後から再現できるようにするため |

### 1.7 HTML出力・検証

| ID | 要件 |
|---|---|
| FR-70 | 案件を単一HTMLに書き出す |
| FR-71 | 書き出し前に検証。重大エラーがあれば出力禁止、警告のみなら出力可 |
| FR-72 | 重大エラー：存在しないノード／ポートへの接続・不正な条件式・無限ループ・実行不能な必須設定（詳細は DATA_MODEL §8） |
| FR-73 | 警告：未使用タグ・到達不能ノード・任意項目の未設定・重複配信の可能性（詳細は DATA_MODEL §8） |
| FR-74 | 書き出したHTMLに、編集機能・APIキー・社内メモが**含まれていないことを機械検査**し、混入があれば出力を中止 |
| FR-75 | **【追加提案】** 書き出したHTMLのフッターに「架空のデータによるデモです」を固定で出す（顧客の手元で一人歩きしたときの誤解防止） |

### 1.8 AI連携（初期版はClaude Code）

| ID | 要件 |
|---|---|
| FR-80 | 各要素に出所を持たせる：`observed`（スクショで確認）／`inferred`（AIが推定・提案）／`approved`（人が承認） |
| FR-81 | Claude Code がスクショから「シナリオ差分JSON」を生成し、編集ツールが読み込んでプレビュー→承認→本体反映する |
| FR-82 | 未承認の `inferred` が残っている案件は、営業用HTMLに書き出せない（**【追加提案】** 要件§11では重大エラーに含まれていないが、推定を稼働仕様として断定しないための仕組みとして重大扱いを推奨） |
| FR-83 | 将来ツール内にAIを積むときは、同じ「シナリオ差分JSON」を出すだけにする（エンジン・編集画面は変えない） |

## 2. 非機能要件

| ID | 要件 | 具体値 |
|---|---|---|
| NFR-01 | 動作環境（編集ツール） | Windows 11 ＋ Chrome／Edge 最新版。Node.js 24（導入済み） |
| NFR-02 | 動作環境（営業用HTML） | Chrome／Edge 最新版。`file://` で開いてネット接続なしで全機能が動く |
| NFR-03 | 起動の手軽さ | 編集ツールは `start.bat` のダブルクリック1回で起動しブラウザが開く。初回のみ依存の自動インストール（数分） |
| NFR-04 | 営業用HTMLのサイズ | 目標 3MB 以下、5MB 超で警告、15MB 超は出力禁止（メール添付を想定） |
| NFR-05 | 応答性 | ユーザー4人・ノード200個・Day 30 までの早送りが 1秒以内 |
| NFR-06 | 決定論 | 同じ案件＋同じ入力イベント列 → 同じ状態（乱数・現在時刻をエンジン内で使わない） |
| NFR-07 | 汎用性 | 共通エンジンのソースに日本語の文字列・業種固有の語を置かない（ビルド時に自動検査して0件） |
| NFR-08 | データ安全 | 保存は「一時ファイルに書いてから置き換え」。書き込み途中で落ちても前の版が残る |
| NFR-09 | 可搬性 | 案件はフォルダ1つ（JSON＋画像）で完結。フォルダごとコピーすれば別PCで開ける |
| NFR-10 | 互換性 | 案件JSONに `schemaVersion` を持ち、古い版は読み込み時に自動変換 |
| NFR-11 | 視認性 | 本文14px以上、表・注記12px以上。資料用表示（FR-53）ではさらに拡大 |
| NFR-12 | アクセシビリティ | キーボード操作・フォーカス表示・`prefers-reduced-motion` 尊重（八十吉デモの水準を下回らない） |
| NFR-13 | 秘密情報 | APIキーは案件JSONに保存しない（将来のAI内蔵時も環境変数か別ファイル） |
| NFR-14 | 将来性 | エンジンはDOM・Node.js API に依存しない純粋なTypeScript。ブラウザでもサーバーでも同じものが動く |

## 3. 要件どうしの矛盾と解消

| # | ぶつかっている要件 | 何が問題か | 解消案 |
|---|---|---|---|
| C-1 | 「無限ループは重大エラー」×「ステップ配信・待機」 | 定期配信など正当なループもある。グラフにループがある＝NGにすると正しいシナリオも弾く | **「時間が進まず、外部入力も待たないループ」だけを無限ループと定義**。待機ノード（1分以上）か入力待ちノードを1つでも含むループは許可。さらに実行時に1回の時間進行あたりの処理回数に上限（1万）を設け、超えたら停止して報告 |
| C-2 | 「並行配信を許可」×「重複配信の可能性は警告」 | 並行を許すと、静的な検査だけでは重複を確定できない | 静的検査は「同じメッセージに到達する経路が2本以上あり、両方に停止条件がない」を警告。実行時は配信台帳で実際の重複をブロックし、除外理由に「重複防止」と出す |
| C-3 | 「除外理由も表示」×「同じ判定ロジック」 | 判定が真偽だけ返す作りだと、後から理由を出せない | **条件式の評価が最初から「結果＋判定の木（トレース）」を返す**。後付けしない（DATA_MODEL §5） |
| C-4 | 「単一HTML」×「画像」×「オフライン」 | 画像を埋め込むとファイルが肥大（リッチメニュー1枚で最大1.2MB）。外部参照はオフラインで切れる | 書き出し時に WebP・横600px に縮小してBase64埋め込み。サイズ予算（NFR-04）で警告／禁止。「画像なし（枠＋ラベル）」書き出しも用意 |
| C-5 | 「汎用」×「サンプルスタッフで検証」 | 検証案件の都合がエンジンに染み出しやすい | エンジンに日本語文字列を置かないことをビルド時に機械検査（NFR-07）。業種の語彙はすべて案件JSON |
| C-6 | 「初期版はAIなし」×「将来AIを積んでも作り直さない」 | 初期版でAI前提の構造を入れないと、後で全面改修になる | 出所フィールド（FR-80）とシナリオ差分JSON（FR-81）を**Phase 2 のデータモデルに最初から入れる**。中身を書くのは Phase 6 |
| C-7 | 「複数ユーザー」×「仮想時間共有」×「停止条件」 | 同時刻に複数ユーザー・複数フローが動くと、処理順で結果が変わりうる | 処理順を固定：時刻 → ユーザーID → フロー優先度 → ノードID。これで決定論（NFR-06）を担保 |
| C-8 | 「離脱防止・サンクス誘導」×「LINE画面」 | この2施策はLINEの外（Webページ）から始まる。友だちになる前の状態がある | 画面の単位を「LINE画面」ではなく**サーフェス**（トーク／リッチメニュー／Webページ／フォーム／ポップアップ）にする。ユーザー状態に「友だちか否か」を持つ |
| C-9 | 「スクショを資料に貼れる品質」×「スクショ機能は不要」 | 通常の画面は余白・比率がばらばらで、切り取るとスライドに収まらない | 資料用表示（FR-53）を用意。機能追加は最小（CSSの表示切替のみ） |
| C-10 | 「Phase 2 でフロー編集」×「Phase 3 で6施策」 | 6施策の要件を見ないとノードの種類・データ構造が決まらない。先にGUIを作ると作り直しになる | **Phase 2 の前半で、エンジン＋JSON＋検証案件の手書きJSON＋CLIでの通し実行を先に作る**（GUIなし）。データモデルが6施策に耐えると確認してから編集画面を作る（ROADMAP 参照） |

## 4. 不足していた仕様と推奨案

| # | 不足 | 推奨案 |
|---|---|---|
| G-1 | 友だちになる前・ブロックの状態 | ユーザー状態に `friendState: not_friend / friend / blocked` を持つ（FR-26） |
| G-2 | ステップ配信の「時刻」 | 「友だち追加から N日後の HH:MM」と「N分後」の2種類。実務では配信時刻を指定するのが普通 |
| G-3 | タグと回答の関係 | タグは平文の文字列（実際のLINE拡張ツールと同じ）。回答は別に `answers` に保存し、条件式から直接参照できる。タグ付与は回答の「結果」として明示的に設定する |
| G-4 | 条件式の保存形式 | 入れ子のJSON（AND/OR/NOT の木）。平らなルール一覧では「(A または B) かつ Cでない」を表せない |
| G-5 | 文面中の差し込み | `{{user.name}}`・`{{answer.<質問ID>}}` 形式の置換。八十吉デモの `.replace` を正式化 |
| G-6 | 配信通数 | **【追加提案・要承認】** 配信1件ごとに通数を数え、裏側パネルに累計を出す。料金プラン（無料枠・従量）を案件設定に持てば月額の目安も出せる。八十吉デモでも「通数：0」を毎場面に出しており、SIM実務の核なので入れる価値が高い。ただし元の指示に無い機能なので採否を確認したい |
| G-7 | 実仕様の上限 | ステップ配信の「開始後○日」は最大365日などLINE側の上限を、検証の警告に入れる |
| G-8 | 削除の意味 | 案件の削除は「ゴミ箱フォルダへの移動」。完全削除は行わない |
| G-9 | 書き出しファイル名・置き場所 | `<案件名>_デモ_YYYYMMDD.html` を `Downloads` 直下に出す（社内の成果物の置き場ルールに合わせる） |
