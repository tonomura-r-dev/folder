# ARCHITECTURE — 推奨技術・システム構成

最終更新：2026-10-26（Phase 1）

---

## 1. 設計の背骨（3つだけ）

1. **エンジンは1本。** 判定・時間進行・配信制御を行う「シナリオエンジン」を、依存ゼロの純粋なTypeScriptで1つだけ作る。編集ツールも営業用HTMLも、将来のWebサービスも、このエンジンをそのまま載せる。
2. **状態は入力イベント列から導出する。** 保存する「真」は「何が起きたか」の列だけ。タグ・配信履歴・進行状況は毎回計算し直す（八十吉デモの「0番から before() をやり直す」を正式化したもの）。
3. **AIは「差分JSONを出す人」として外に置く。** Claude Code が出すか、将来ツール内のAIが出すかの違いだけにする。

## 2. 全体構成

```
line-simulator/
├─ packages/
│   ├─ engine/          ← シナリオエンジン（純TS・依存ゼロ・DOMなし・日本語なし）
│   │    schema / validate / evaluate(条件式) / reduce(イベント→状態) / scheduler / patch
│   ├─ player/          ← デモ画面（LINE・Web・裏側パネル）。編集ツールと営業用HTMLで共用
│   └─ editor/          ← 編集ツール（React＋フローチャート）。社内専用
├─ tools/
│   ├─ export.ts        ← 営業用HTMLの書き出し
│   ├─ run.ts           ← CLIでシナリオを通し実行（Phase 2 の検収に使う）
│   └─ check-engine.ts  ← エンジンに日本語・業種語が混ざっていないかの検査
├─ projects/            ← 案件フォルダ（1案件＝1フォルダ）
│   └─ sample-staff/
│        project.json   ← シナリオ設定
│        sessions/      ← デモ状態（ユーザー・イベント列）。設定とは別
│        assets/        ← 画像
│        history/       ← 保存ごとのスナップショット
├─ .trash/              ← 削除した案件の退避先
├─ docs/
└─ start.bat            ← ダブルクリックで起動
```

依存の向き（逆向きは禁止）：

```
editor ──▶ player ──▶ engine
export ──▶ player ──▶ engine
run    ───────────▶ engine
```

`engine` は何にも依存しない。`projects/` を読み込むのは `editor`／`export`／`run` だけ。

## 3. 技術選定

### 3.1 前提条件

| 条件 | 中身 |
|---|---|
| 使う人 | エンジニアではない営業担当。起動はダブルクリックで済ませたい |
| 環境 | Windows 11、Chrome／Edge、Node.js 24・npm 11 導入済み |
| 書き出し先 | ネットなしで開く単一HTML |
| 将来 | Webサービス化・AI内蔵 |

### 3.2 編集ツールの土台

| 候補 | 良い点 | 弱い点 | 判定 |
|---|---|---|---|
| **Vite＋React＋TypeScript** | 開発が速い／フローチャート部品が揃う／型でデータ構造を守れる／Webサービス化でそのまま使える | 初回に `npm install` が要る（`start.bat` で自動化） | **推奨** |
| ビルドなしの素のJS | インストール不要 | フローチャート編集を自作することになり工数が大きい。型がない | 不採用 |
| Electron／Tauri | デスクトップアプリになる | 配布・更新の手間。今は不要 | 不採用（将来も Web 化の方が自然） |
| Svelte／Vue | 軽い | フローチャート部品の選択肢が少ない | 不採用 |

### 3.3 フローチャートUI

| 候補 | ライセンス | 良い点 | 弱い点 | 判定 |
|---|---|---|---|---|
| **@xyflow/react（React Flow）** | MIT | 事実上の標準。ノード追加・接続・移動・ズーム・ミニマップが揃う。独自ノードを自由に作れる | Reactが前提 | **推奨**（有料の Pro 版は使わない） |
| Rete.js | MIT | ノードエディタ専用で高機能 | 概念が多く学習コストが高い | 不採用 |
| Drawflow | MIT | 素のJSで軽い | 接続線・見た目の自由度が低い | 不採用 |
| LiteGraph | MIT | 高速 | Canvas描画で見た目が古い。HTMLで独自ノードを作りにくい | 不採用 |
| 自作SVG | — | 依存ゼロ | 接続・ズーム・選択などで工数が膨らむ | 不採用 |

React Flow は**自前の薄いラッパー経由でだけ使う**（将来のメジャー更新や乗り換えの影響を `editor/flow/` の中に閉じ込める）。

### 3.4 シナリオエンジン

| 候補 | 判定 | 理由 |
|---|---|---|
| **自作（純TS・依存ゼロ）** | **推奨** | 判定理由の木（トレース）を返す必要がある。営業用HTMLに埋め込むので依存ゼロが望ましい。決定論を自分で保証できる |
| json-logic-js（条件式ライブラリ） | 不採用 | 結果の値しか返さず、「どの条件で外れたか」が取れない（要件§6の除外理由が出せない） |
| XState（状態機械ライブラリ） | 不採用 | 「ユーザーごと・フローごとに待機タイマーがある」構造に合わない。営業用HTMLに依存が増える。巻き戻し（任意のDayへ戻る）は単純な reducer の方が楽 |

エンジンの決まりごと：

- DOM・Node.js API・`Date.now()`・`Math.random()` を使わない（時刻は仮想時間を引数で受け取る）
- 画面に出す文字列を持たない（ラベルはすべて案件JSONか、player側の辞書）
- 公開する関数は純関数だけ：`validate(project)`／`evaluate(expr, ctx)`／`reduce(project, events)`／`applyPatch(project, patch)`

### 3.5 保存

| 候補 | 判定 | 理由 |
|---|---|---|
| **ディスク上のJSONファイル＋開発サーバーの小さなAPI** | **推奨** | Vite の開発サーバーに `/api/projects/*` を足すだけ（数十行・追加依存なし）。JSONなのでgitで差分が見える。DB不要 |
| ブラウザの File System Access API | 補助 | Chromeでは使えるが、毎回フォルダ選択が要る |
| JSONのダウンロード／アップロード | 常備 | 要件のJSONインポート／エクスポートとして必ず作る。上記が壊れたときの逃げ道にもなる |
| IndexedDB／localStorage | 不採用 | ブラウザの中に閉じて見えない・消える。フォルダごとのコピー（NFR-09）ができない |

保存は「`project.json.tmp` に書く → 置き換え」で行い、置き換え前に `history/` へスナップショットを取る。

### 3.6 営業用HTMLの書き出し

```
tools/export.ts <案件>
  1. project.json を読む
  2. engine.validate → 重大エラーがあれば中止
  3. 社内専用の項目を取り除く（internal／_internal／出所メモ）
  4. 画像を Base64 化（横800pxより大きい・300KBより重い画像は WebP に縮小）
  5. テンプレートHTMLに、エンジン（1本のJSに束ねたもの）・player・案件JSON・CSS を埋め込む
  6. 出来上がったHTMLを検査：社内項目・APIキーらしき文字列・編集ツールのコード・外部URL が無いこと
  7. サイズ判定（5MB超で警告／15MB超で中止）
  8. Downloads 直下に <案件名>_デモ_YYYYMMDD.html として保存
```

- JSの束ね（バンドル）は **Vite の build（中身は rolldown）**。追加のツールは要らない（Phase 5 で Vite 8 に合わせて変更）
- HTMLに通信禁止の設定（CSP：`default-src 'none'; img-src data:` ほか）を入れ、外部の読み込みをブラウザに禁止させる
- 書き出す前に「架空または匿名化したデータだけ」の確認を必須にする（自動では見分けられないため）
- 書き出したHTMLは `fetch`・`localStorage`・外部フォント・外部スクリプトを一切使わない（`file://` で開くと使えない・使えても不安定なため）。状態はすべてメモリ上
- フォントはシステムフォント（`Meiryo, "Yu Gothic UI", sans-serif`）。Windows には必ず入っている
- 編集ツールの画面からもボタン1つで書き出せる（開発サーバーのAPI経由で同じ `export.ts` を呼ぶ）

### 3.7 テスト

| 種類 | 道具 | 対象 |
|---|---|---|
| 単体 | Vitest（Viteと相性がよい） | 条件式の評価・検証・時間進行 |
| 通し | `tools/run.ts`＋スナップショット | 検証案件を4ユーザーで Day 30 まで流し、結果（配信履歴・タグ）を固定ファイルと比較 |
| 画面 | ブラウザで目視＋PNG | 各Phaseの終わりにスクショで確認 |
| 書き出し | `export.ts` の検査ステップ | 社内項目の混入・サイズ |

## 5. 将来への拡張

### 5.1 Webサービス化

| 今 | Webサービス化後 | 変わるもの |
|---|---|---|
| Vite開発サーバーの `/api/projects/*` | 本物のAPIサーバー | APIの実装だけ。編集画面は同じURLを叩く |
| ディスクのJSON | DBの1行（JSON列） | 保存先だけ。データ構造は同じ |
| エンジンはブラウザで実行 | サーバーでも同じエンジンを実行可能 | なし（純TSなので） |
| 1人で使う | ログイン・権限・案件の共有 | 追加開発。案件JSONに `owner` 等を足す余地を残す |

### 5.2 AI内蔵

```
 初期版：  スクショ ─▶ [Claude Code] ─▶ シナリオ差分JSON ─▶ 編集ツールで読み込み ─▶ 承認 ─▶ 本体反映
 最終版：  スクショ ─▶ [ツール内AI]  ─▶ シナリオ差分JSON ─▶（同じ）
```

- 差し替わるのは真ん中の箱だけ。差分JSONの形・プレビュー画面・承認の仕組み・エンジンは同じ
- ツール内AIは**サーバー側**で呼ぶ（APIキーをブラウザやHTMLに置かない／NFR-13）。ローカル版のうちは開発サーバーがその役
- チャットでの修正も「差分JSONを返す」に揃える。AIに案件JSONを丸ごと書き換えさせない（どこを変えたかが見えなくなるため）

## 6. 採用ライブラリ一覧（予定）

| 用途 | ライブラリ | ライセンス | 営業用HTMLに入るか |
|---|---|---|---|
| 編集画面 | React, React DOM | MIT | 入らない（playerは素のDOMで書く） |
| フローチャート | @xyflow/react | MIT | 入らない |
| 開発サーバー・束ね | Vite（rolldown同梱） | MIT | 入らない |
| 型 | TypeScript | Apache-2.0 | 入らない |
| テスト | Vitest | MIT | 入らない |
| 画像縮小 | sharp | Apache-2.0 | 入らない（書き出し時のみ） |

**営業用HTMLに入るのは、自作の engine と player だけ（外部ライブラリゼロ）。**
player を React で書かないのは、営業用HTMLを軽く・長持ちさせるため（八十吉デモと同じ素のDOM描画）。編集ツールの中でも同じ player を埋め込んで使う。

バージョンは導入時点の安定版に固定し、`package-lock.json` をコミットする。有料版・有料APIは使わない。
