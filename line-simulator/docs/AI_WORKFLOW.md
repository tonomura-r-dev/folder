# AI_WORKFLOW — スクリーンショットからシナリオ案を作る流れ

最終更新：2026-10-27（Phase 6）

既存のLINE公式アカウントのスクリーンショットから、Claude Code がシナリオ案（**シナリオ差分JSON**）を作り、
人が編集ツールで確かめて取り込み・承認してから、デモ・営業用HTMLに使う。初期版はツールにAIを内蔵しない。

```
 スクショ ─▶ [Claude Code] ─▶ シナリオ差分JSON ─▶ 編集ツール「AI提案」で確認・取り込み ─▶ 承認／修正／却下 ─▶ デモ・書き出し
             （見えたもの＝確認済み／              （ここで人が選ぶ）                    （承認するまで
               推定したもの＝AI推定）                                                    書き出せない）
```

将来ツール内にAIを積むときは、真ん中の箱（Claude Code）を置き換えるだけ。差分の形・確認画面・承認の仕組み・エンジンは変えない。

---

## 1. 出所の3区別（いちばん大事な決まり）

| 区別 | 意味 | 付ける人 | 営業用HTML |
|---|---|---|---|
| **確認済み**（observed） | スクショに**写っている**もの。文面・メニューの文字・ボタンの文字・画面の並び | AI（どのスクショか `source` を必ず書く） | 書き出せる |
| **AI推定**（inferred） | スクショに写っていない**推定・提案**。分岐の条件・タグ・配信の日時・停止条件・アンケートとタグの対応・CVの定義・シナリオのつながり・ペルソナ | AI（なぜそう考えたか `rationale` を必ず書く） | **承認するまで書き出せない** |
| **承認済み**（approved） | AI推定を、人が中身を確かめて承認したもの | **人だけ**（AIは付けてはいけない） | 書き出せる |

- 推定した分岐やタグを、既存アカウントで**実際に動いている仕様として扱わない**。あくまで提案。
- 出所のメモ（`prov`）は営業用HTMLには入らない（書き出し時に取り除く）。

## 2. 人がやること（準備）

1. 編集ツールで案件を作る（既存の案件に足すなら、その案件を使う）。フォルダ名をメモする（例：`sample-beauty`）。
2. スクショを `line-simulator/projects/<フォルダ名>/screenshots/` に置く。
   - このフォルダは**リポジトリに入らない**（`.gitignore`）。実在アカウントのスクショは顧客の資料として手元だけで扱う。
   - ファイル名は撮った順に番号を付ける（`01_richmenu.png` など）。
3. 撮るもの（あるものだけでよい）

| # | 画面 | 分かること |
|---|---|---|
| 1 | リッチメニュー全体 | 区画の並び・文字・押したときの動き（ページか、メッセージか） |
| 2 | 友だち追加直後のトーク | 挨拶の文面・最初に出るボタンやアンケート |
| 3 | 自動応答のやり取り | キーワードと返信の文面 |
| 4 | 配信の例（クーポン・お知らせ・リマインド） | 文面・ボタン。届いた日（何日目か）が分かれば一緒に |
| 5 | アンケート・診断の画面 | 質問と選択肢 |
| 6 | Webの予約・応募フォーム、完了ページ、離脱時のポップアップ | フォームの項目・完了後のLINE誘導 |

4. Claude Code に頼む：**「`<フォルダ名>` のスクショからシナリオ案を作って」**（スキル `line-sim-screens` が動く）

## 3. Claude Code がやること

1. スクショを1枚ずつ読み、**見えたもの一覧**を作る（文面は写っているとおりに書き写す）。
2. 案件の `project.json` を読み、いまあるID・部品を確かめる（重ならないIDを使う）。
3. シナリオ差分JSON（`docs/DATA_MODEL.md` §10 の `ScenarioPatch`）を作る。
   - **1つの提案＝人が「採る／採らない」を決められる1つのまとまり**（文面1つ、メニュー1つ、シナリオ1本〈ノードと線ごと〉など）。
   - 配列には1件ずつ `"/messages/-"` のように追加する（まとめて置き換えない）。
   - 写っているものは `prov: { state: "observed", source: "screenshot:02_greeting.png" }`。
   - 推定したものは `prov: { state: "inferred", rationale: "…だから…と考えた" }`。
   - シナリオ1本の中に、写っている文面（確認済み）と推定のつながり（AI推定）が混ざるときは、ノードごとに `prov` を付ける。
   - **固有名詞は伏せる**：会社名・店名・人名・電話番号・URLは `〔店名〕` などに置き換え、案件の会社名は「〇〇サンプル（仮）」にする。伏せた場合は `source` に「固有名詞は伏せ字」と書く。
   - `approved` は**付けない**。
   - デモで流せるよう、ペルソナと台本も推定として足す（例：カット希望の人・カラー希望の人）。
4. `line-simulator/projects/<フォルダ名>/patches/<YYYYMMDD-HHmm>_<短い名前>.json` に保存する。
5. 検査を流し、OK になるまで直す。

```bash
npm run patch:check -- <フォルダ名> <提案ファイル名>
```

   - 形の誤り・当たらない場所・承認待ち以外の重大エラーがあれば NG。「AI推定が承認されていない」は正常（件数だけ出る）。
6. 報告する：見えたもの一覧／推定したもの一覧（根拠つき）／**確かめてほしい点**（推定の中で特に自信が無いもの）。

## 4. 人がやること（確認・承認）

1. 編集ツールで案件を開き、左の **「AI提案（スクショから）」** を押す。
2. 提案ファイルを選ぶ。提案が1件ずつ「出所（確認済み／AI推定）・内容・根拠」で並ぶ。
   - 要らない提案はチェックを外す（＝**却下**）。「確認済みだけ」ボタンで写っていたものだけにもできる。
   - 選んだ分を当てたときの重大エラーの数が、その場で出る。
3. 「選んだ提案を下書きに取り込む」。
4. **承認待ちのAI推定**の一覧で、1件ずつ
   - **承認**：中身が正しければ。
   - **開いて直す**：その部品の編集画面へ飛ぶ（直したら、その画面の「内容を確かめて承認する」で承認）。
   - **却下**：取り除く（シナリオのノードなら、出入りする線も一緒に消える）。
   - フローチャートのノードや各一覧にも「確認済み／AI推定／承認済み」の印が出る。
5. 保存 → 「▶ デモ」で動きを確かめる → 「営業用HTMLを書き出す」。
   - 承認待ちが1件でも残っていると、**重大エラー「AIの推定が承認されていません」で書き出せない**。
