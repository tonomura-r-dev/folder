# トレンドレポート作成スキル

殿村さん（DYM）が毎月作る社内向け資料。「LINE公式アカウント 媒体最新情報 ◯月 トレンドレポート」。
LINEヤフー社の更新情報（テキストの箇条書きやPDF）を、過去に実際配布された号と同じトンマナのPPTXに変換する。

## 全体の流れ（1ヶ月分）

1. **ネタ出し**：殿村さんが「媒体最新情報」の一覧（トピック名＋概要＋出典URL、TSV/表形式が多い）を貼る
2. **構成案を作る**：全トピックをスライド構成（表紙／目次／各トピック）に整理する
3. **PPTX化**：`_build/trend_report_engine.py` を使ってFMTトンマナでPPTX生成
4. **アジェンダを上長確認に回す**：殿村さんが上司にリストを見せ、採否コメントをもらってくる。「先月やった」「期限切れ」「優先度低いので後ろ／除外」等の指示をそのままアジェンダに反映
5. **PDFで肉付け**：各トピックについてLINEヤフー社の詳細資料（PDF）が送られてくるので、4区分（概要・変更点／料金体系・出稿条件／スケジュール・導入フロー／注意点・影響）に該当箇所を振り分けて追記
6. **毎回 commit & push、ファイルを送る**

途中で何度もPDFが送られてくる・アジェンダが変わる・同じPDFが重複して再アップロードされる、というのが通常運転。**慌てず現状のTOPICS構造を1件ずつ更新していけばよい。**

## トンマナの正体（★最重要・何度も差し替えが起きた経緯）

このリポジトリには紛らわしいFMTが3つある。**トレンドレポートで使うのは3番目だけ。**

| ファイル | 中身 | 使い道 |
|---|---|---|
| `_templates/DYM_LINEOA_FMT.pptx` | 提案書系FMT（中身は人材業界の提案書が元） | `lineoa-industry` スキルの資料生成用。トレンドレポートでは**使わない** |
| `_templates/DYM_LINEOA_BUFFF_FMT.pptx` | 別の営業資料（LINEOA運用提案） | 2026-09に一度これで作ったが「トンマナが全然違う」と指摘され不採用になった **黒歴史。使わない** |
| `_templates/DYM_LINEOA_TREND_FMT.pptx` | **2026年7月号トレンドレポートの実ファイルそのもの** | ★これが正本。2026-09-16、殿村さんから6月号・7月号の実ファイルを提供してもらい確定 |

3つとも「DYMのネイビー系トンマナ」で見た目が似ているため混同しやすい。**トレンドレポートを触るときは必ず `DYM_LINEOA_TREND_FMT.pptx` を使っているか確認すること。**

## ファイル構成

| パス | 役割 |
|---|---|
| `_templates/DYM_LINEOA_TREND_FMT.pptx` | トンマナの正本（2026年7月号の実ファイル） |
| `_build/trend_report_engine.py` | 共通エンジン。**月をまたいで使い回す。基本触らない**（デザインの指示があったときだけ） |
| `_build/build_trend_report_YYYYMM.py` | 月次データ（TOPICS）だけを持つ薄いスクリプト |
| `LINEOA媒体最新情報_YYYY年M月トレンドレポート.pptx` | 出力（リポジトリ直下） |

### 新しい月を始めるとき

`_build/build_trend_report_202609.py` を同じ月数字違いでコピーして、`MONTH_LABEL` / `OUT` / `TOPICS` を書き換えて `engine.build(OUT, MONTH_LABEL, TOPICS)` を呼ぶだけ。`trend_report_engine.py` は触らない。

## エンジンの仕組み（`trend_report_engine.py`）

FMTを直接いじるのではなく、**FMTの中の実在するスライドを複製して中身を書き換える**方式。

1. `_templates/DYM_LINEOA_TREND_FMT.pptx` をコピーし、表紙(0)・目次(1)・トピックのひな形(2＝【LINE VOOM】のページ)の3枚だけ残す
2. `duplicate_slide()` でひな形をトピック数ぶん複製する（同じスライドレイアウトを使うだけで、新しいレイアウトは作らない）
3. 各スライドの中身をテキストだけ書き換える：
   - **表紙**：タイトル文言を書き換えるだけ（`edit_cover`）
   - **目次**：1つのテキストボックスの段落を増減して `P.3　【ブランド】見出し` の行を並べる（`edit_agenda`）
   - **各トピック**：
     - バナー見出し（`【bracket】headline`）
     - 対象業界の値ボックス
     - 4つの分類タグ（LINE公式アカウント／開発LINE API／オプション商材／その他）のうち1つだけハイライト（`set_tag_highlight`）
     - 3行の説明バンド（段落数3・中央揃えという構造で自動特定するので、**description_linesは必ず3行**にする）
     - 出典URL
     - 本文の表（ひな形の「実施日／内容／影響」3列×7行の表は削除し、**4行×2列（区分／内容）の表に作り直す**。理由：過去号は毎回テーブル構成がバラバラで再現しきれないため、既存のTOPICSデータ構造（overview/pricing/schedule/caution）をそのまま流し込める固定4行に統一した）

ヘッダーの「今後のアップデート情報」・DYMロゴ・区切り線・フッター・認知/検討/獲得/伸長の逆三角形図は**ひな形をそのまま複製しているだけで、触らない**（静的な装飾なのでトピックごとに変える必要はない）。

### TOPICSの1件のキー

```python
dict(
    bracket="LINEミニアプリ",              # バナーの【】内
    headline="お気に入り追加促進機能のご案内",  # バナーの残り。bracket+headlineで1行に収まる長さに（目安30字前後、長いと2行に折り返して下の帯と重なる）
    industry="友だち獲得を強化したい全業種",   # 対象業界ボックスの値
    category="LINE公式アカウント",          # 4タグのうちどれをハイライトするか。"開発\nLINE API" / "オプション\n商材" / "その他" のいずれか（タグの実テキストと完全一致させる）
    description_lines=[...],              # 必ず3行。3行に収まるよう文を分ける
    overview=[...], pricing=[...], schedule=[...], caution=[...],  # 本文4区分（旧エンジンと同じキー名のまま流用可）
    source="https://...",
)
```

`title`（目次に出すページタイトル）はビルドスクリプト側で `f"【{bracket}】{headline}"` を自動生成すればよい。

## データの集め方・落とし穴

- **`workers-hub.box.com` はこの実行環境からegressブロックされていて中身を見られない。** 出典URLとして記載するだけにして、内容確認は殿村さんからPDF／テキストで送ってもらう
- PDFは同じ内容が複数回・別ファイル名で再アップロードされることがある（ページ数や容量が完全一致していれば重複とみなしてよい）。新しく届いたPDFが本当に新規情報かどうかは、既存TOPICSの該当トピックと見比べて判断する
- 大きいPDF（1ファイルが数MBや十数ページ超）は `Read` ツールに `pages` パラメータが必須になる。まず先頭数ページで構成を把握してから必要な範囲を追加で読む
- PDFの内容を4区分に振り分けるときの目安：
  - **概要・変更点**：何がどう変わるか（AS-IS→TO-BEがあれば必ず入れる）
  - **料金体系・出稿条件**：金額・通数・掲載期間など。無ければ「該当なし」
  - **スケジュール・導入フロー**：リリース日・申請〜掲載までの営業日フロー
  - **注意点・影響**：FAQ・キャンセル規定・影響範囲・要確認事項
- 上長確認で「除外」「書き直し」「優先度低いので後ろ」等の指示が出たら、`TOPICS` の順番そのものを並び替え・削除する（目次は自動生成なのでズレる心配はない）
- **1トピックあたりの情報量に上限がある。** 4区分の表は高さが決まっており、内容が多すぎると自動でフォントが縮む（`rebuild_body_table()` 内、文字数で3段階：120字未満11pt／120〜200字9.5pt／200字超8.5pt）が、それでも多すぎるとページ下端やフッターにはみ出す。**PDFの内容を全部盛り込もうとせず、区分ごとに要点を3〜5行程度に絞る。** 迷ったら文言を削る方を優先し、レイアウト側の数値はいじらない

## ビルド〜納品の手順

```bash
python3 _build/build_trend_report_202609.py
```

出力後は必ず見た目を確認してから渡す（文字あふれ・バナー見出しの2行折り返し・表の下端がフッターと重なっていないか）。

```bash
rm -f "LINEOA媒体最新情報_2026年9月トレンドレポート.pdf"
soffice --headless --convert-to pdf "LINEOA媒体最新情報_2026年9月トレンドレポート.pptx"
python3 -c "
import fitz
doc = fitz.open('LINEOA媒体最新情報_2026年9月トレンドレポート.pdf')
for i, page in enumerate(doc):
    page.get_pixmap(dpi=120).save(f'/tmp/.../slide{i+1:02d}.jpg')
"
```

生成したJPGをReadツールで全ページ確認する。`libreoffice-impress` と `poppler-utils`（pdftoppm用。使わなくてもPyMuPDFでフォールバックする）が入っていないことがあるので、無ければ `apt-get install -y libreoffice-impress poppler-utils` を入れる。

確認できたら commit & push し、`SendUserFile` で殿村さんに渡す。**社内配布物なのでコミットして問題ない**（クライアント個別の金額等が入る資料とは違う）。

## 大きな仕様変更をするとき

殿村さんから「表紙とトピック1だけ先にデモで見せて、OKなら全ページ」のように言われたら、**必ずデモを先に作って確認を取ってから全トピックに展開する。** 全ページ一気に作り直して後から手戻りになるより、2枚だけの軽いデモで合意を取るほうが速い（2026-09-16の実例：デモ→承認→全6トピック展開、という流れで進めた）。
